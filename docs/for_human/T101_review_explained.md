# T101 任务与 Review 通俗解释

更新日期：2026-05-14

## 一、这个任务在做什么（通俗版）

### 背景一句话

上一轮（T100）我们已经"打开箱子看了一眼，画好了结构图"，知道了 WeFlow 导出的聊天记录有哪些字段。但看之前和看之后都有一个核心问题：**怎么保证这些包含私人对话的文件不会被意外公开？**

### 为什么需要这个任务

T100 确认了数据可解析，但也发现了一个严峻事实——文件名里直接包含了真实联系人姓名（比如 `私聊_某某.jsonl`），消息里包含了真实平台 ID、真实消息 ID、真实头像路径等大量可以直接或间接识别出具体个人的信息。

如果后续写代码解析这些文件时，一不小心把某个真实 ID 或一段真实对话复制到了文档、示例文件或测试用例里，这些信息就会跟着代码一起提交到 git 仓库——可能被任何人看到。

所以 T101 要做的是：**在写任何解析代码之前，先把"什么可以公开、什么绝对不能公开"的规则白纸黑字写清楚。**

### 具体做了什么

1. **给数据分了三个区域**：
   - `private/`（保险柜）：原始聊天记录和中间产物，永远不提交到 git
   - `docs/`/`examples/`/`tests/`（公开区）：只允许出现假名字、假内容、假 ID
   - 规定了哪些字段可以在哪个区域出现

2. **列出了四类需要保护的敏感信息**：
   - 直接标识（真名、平台 ID、消息 ID 等）
   - 聊天原文（包括引用内容和转发记录）
   - 联系人元数据（头像、会话名称等）
   - 嵌套个人信息（聊天中出现的手机号、地址、身份证等）

3. **规定了三种安全替换方式**：
   - 稳定别名：`ACCOUNT_SELF`、`CONTACT_A`、`file_01` 等
   - 哈希别名：`pmid_a1b2c3d4`、`evt_xxx` 等（用不可逆算法生成）
   - 合成文本：`[SYNTHETIC] neutral sample text`（完全人工编造）

4. **定义了证据引用规则**：
   - 每条消息需要一个"来源标记"（source_ref），能追溯到原始文件
   - 但这个标记只能用假名和行号（`weflow:file_01:4`），不能用真实文件名

5. **列出了五条红线**（违反任何一条就算失败）：
   - 公开区域出现真实聊天原文
   - 出现真实联系人姓名
   - 出现真实消息 ID
   - 用"只遮一半"的方式保留可回推身份的信息
   - 稍改几个字就当"脱敏样例"

6. **更新了示例文件**：在之前的 5 行合成样例基础上，给消息行加了 `eventIdPreview`、`sourceRefPreview`、`rawRefPreview` 三个展示字段，直观展示"公开区域里的引用长什么样"。

### 打个比方

T100 是"打开箱子画结构图"，T101 就是"贴标签和上锁"：

- 给保险柜贴上"禁止带出"的标签
- 给每样东西编上假名字
- 写清楚"什么可以搬出保险柜、什么不可以"
- 确认所有贴出去的标签上都是假名字

**还没做的事**：按这些规则真正去处理数据——这要等 T102 写代码。

## 二、任务的详细技术解释

### 2.1 任务目标

T101 的正式目标是：**设计本项目处理 WeFlow 聊天记录的隐私脱敏规则、source_ref/raw_ref 规则和最小红线测试样例。**

这来自项目实验计划（`docs/02_experiment_plan.md`）的 Milestone 0 阶段，也是离线蒸馏管线的隐私护栏。在 T102 写 normalize CLI 之前，必须把这些规则固定下来，否则后续所有任务都可能把私密内容带进可提交目录。

### 2.2 任务流程

```
读取 T100 交付产物（schema profile + normalized event contract）
  ↓
识别 T100 发现的 11 个隐私风险字段
  ↓
定义数据区域规则（private/ vs docs/examples/tests）
  ↓
分类 PII（直接标识 / 原文 / 元数据 / 嵌套个人信息）
  ↓
设计替换策略（稳定别名 / 哈希别名 / 合成文本）
  ↓
定义 source_ref 和 raw_ref 的公共形态与红线
  ↓
更新样例 fixture，加入 source_ref/raw_ref 预览字段
  ↓
更新 handoff 文档
```

### 2.3 代码变化/配置变化

本次任务**没有修改任何源代码**，只产生了文档和样例更新。

| 文件 | 变化类型 | 说明 |
| --- | --- | --- |
| `docs/data_contracts/privacy_redaction_rules.md` | 新增 | 隐私脱敏规则：PII 分类、数据区域规则、字段处理矩阵、替换策略、红线清单 |
| `docs/data_contracts/source_ref_rules.md` | 新增 | 证据引用规则：别名格式、行号规则、消息 ID 规则、source_ref/raw_ref 格式、各目录允许/禁止清单 |
| `examples/payloads/weflow_redacted_sample.jsonl` | 修改 | 两条 message 行追加 `eventIdPreview`、`sourceRefPreview`、`rawRefPreview` 字段 |
| `docs/07_handoff.md` | 修改 | 更新状态为"worker 交付已出，待 review"，新增 T101 产物记录 |

**没有变化的**：
- `src/practical_chat_agent/**` — 主仓库业务代码完全没动
- `docs/04_task_board.md` — 任务板没动（按规定只能由 Captain 更新）
- `docs/08_risks_and_open_questions.md` — 在允许列表但不在必改列表，worker 未改是正确的
- `private/chat_history/**` — 原始数据只读不写

### 2.4 对后续开发的意义

T101 的规则不是"写在纸上看看"的文档，它们会直接约束后续所有触碰聊天数据的任务：

1. **T102（normalize CLI）**：adapter 代码必须遵守 Field Handling Matrix——真实文件名转 `file_XX`，真实消息 ID 转哈希别名，原始内容只在 `private/distilled/` 中保留。违反就是红线。

2. **T110-T114（离线蒸馏 MVP）**：chunk summary、memory fact、ContactSkill 的内容都受脱敏规则约束。即使是在 `private/` 内部的蒸馏产物，如果未来可能离开 `private/`，也必须先转成安全形态。

3. **T150/T151（评估与硬化）**：隐私泄露测试（T151）的直接检查清单就是 T101 的红线清单。测试用例的输入也必须是合成/脱敏 fixture。

4. **source_ref 规则保证证据链可追溯**：每条 memory fact、每个 ContactSkill claim 都需要 evidence_refs。source_ref 规则确保这些引用能回到本地原始 JSONL 行（`weflow:file_01:4`），同时不泄露真实文件名。这是整个"可审计"原则的基础。

5. **项目路线图定位**：根据 `04_task_board.md`，当前处于 Milestone 0 的后半段。T100 确认了"数据长什么样"，T101 确认了"什么能公开、什么不能"。T102 会把这两者的结论落地为可执行代码。T103 是 M0 的总 review gate——只有 schema、隐私规则、最小 CLI 都通过了，才能进入 M1（离线蒸馏 MVP）。

## 三、为什么 Reviewer 给出了 PASS

### 3.1 Review 做了什么

Reviewer 独立检查了以下内容：

1. **读了任务包**：确认 T101 要求做什么、禁止做什么
2. **看了所有改动**：确认 worker 只改了允许的 4 个文件
3. **隐私扫描**：用真实文件名列表（含联系人姓名）逐一比对交付文件，确认零泄露
4. **规则覆盖度检查**：逐条比对 T100 发现的 11 个隐私风险字段是否都被新规则覆盖
5. **样例安全性检查**：重新解析 JSONL，检查新增 preview 字段的值是否安全
6. **文档质量检查**：看有没有把计划写成已完成事实

### 3.2 PASS 的核心理由

| 检查维度 | 结论 | 说明 |
| --- | --- | --- |
| **是否完成任务** | 是 | 4 项具体要求全部完成 |
| **是否越界** | 没越界 | 只改了允许的 4 个文件，没碰源代码和任务板 |
| **隐私是否安全** | 安全 | 真实联系人姓名和文件名零出现；样例全部合成 |
| **规则是否完整** | 完整 | T100 的 11 个隐私风险字段全部被规则覆盖 |
| **有没有造假** | 没有 | 规则是真正的设计定义，样例是手工合成内容 |
| **是否过早宣称完成** | 没有 | 明确写"本轮只定义规则，不实现脱敏器"；handoff 写"待 review" |
| **有没有过度工程** | 没有 | 两份文档各聚焦一个主题，没有交叉冗余 |
| **是否破坏已有功能** | 没有 | 零代码变更；sample fixture 只做了追加字段，未修改已有内容 |

### 3.3 三个小提醒（Non-blocking Issues）

1. **样例仍未覆盖系统消息和转发记录**：这是 T100 阶段就识别的问题（T100 N02），T101 的任务范围不要求解决它，但后续 T102/T150 需要补充。

2. **preview 字段的 hex 值太规整**：`a1b2c3d4` 是手工编的可读序列，不是真实哈希。作为 fixture 注释完全可以，但如果有人直接复制当模板可能困惑。风险很低。

3. **结构化替换 token 是前瞻设计**：`[PHONE]`、`[EMAIL]` 等脱敏占位符是为未来脱敏器准备的规范，当前阶段不实现。文档措辞谨慎（"若未来需要"），没有声称已实现。T102 实现时需要校验这些 token 是否对齐实际需求。

这三个提醒都不影响 T101 通过。
