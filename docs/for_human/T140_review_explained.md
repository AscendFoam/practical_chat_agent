# T140 Review Explained - 通俗解释

## 1. 这个 Task 在做什么？（通俗版）

想象你在使用一个"回复助手"：它根据你和某位联系人的历史互动，帮你生成几个候选回复草稿。你看完这些草稿之后，可能有几种反应：

- **accept**：这个草稿不错，直接用。
- **edit**：方向对了，但我想改几个字。
- **reject**：这回复不行，不用了。
- **boundary**：这个回复触碰到了关系边界（比如太亲密、太冒犯、话题不合适）。

T140 做的事情很简单：**把这些反馈记录下来**，写到一个本地的私有文件里。就像一个笔记本，记下你对每个草稿的看法。

关键约束：**只记录，不行动**。它不会自动修改你的联系人画像、记忆库，也不会自动发送任何东西。纯粹是"收集意见"。

## 2. 实现细节

### 任务目标

T140 是 Milestone 4（反馈闭环）的第一个任务。它要定义一个"反馈日志"的数据格式，并实现一个命令行工具（CLI），让你可以手动记录对回复草稿的反馈。

这个任务承接了 M3（联系人感知回复规划器）的成果。在 M3 中，系统已经能够根据联系人信息生成多个候选回复。现在需要一个机制来收集你对这些候选的反馈，为后续的"反馈驱动的偏好更新"打基础。

### 代码变化

#### 2.1 数据模型 (`src/practical_chat_agent/core/models.py`)

新增了三个数据结构：

- **`ReplyFeedbackAction`**：一个类型定义，限定反馈动作只能是 `accept`、`edit`、`reject`、`boundary` 四种之一。
- **`ReplyFeedbackRecord`**：一条反馈记录。包含：
  - `feedback_id`：自动生成的唯一标识符
  - `created_at`：创建时间
  - `contact_id`：联系人 ID
  - `reply_plan_id`：来源回复计划的 ID
  - `candidate_id` / `priority_rank`：你选择了哪个候选草稿
  - `action`：你的反馈动作
  - `user_note`：你的备注（可选）
  - `edited_text`：如果动作是 `edit`，你改了什么（可选）
  - `boundary_label` / `boundary_note`：如果动作是 `boundary`，具体是什么边界问题（可选）
  - `source_plan_path`：来源计划文件的路径（可选）
- **`ReplyFeedbackLog`**：一个日志容器，包含多条 `ReplyFeedbackRecord`，有版本号和生成时间。

#### 2.2 反馈服务 (`src/practical_chat_agent/services/feedback.py` - 新文件)

新增 `FeedbackService` 类，负责核心逻辑：

1. **加载回复计划**：读取你指定的 `ReplyPlan` JSON 文件，用 Pydantic 校验格式是否正确。
2. **验证候选**：检查你指定的候选排名（如第1名、第2名）是否真的存在于这个计划中。如果不存在，报错并列出有效排名。
3. **记录反馈**：根据你的输入创建一条 `ReplyFeedbackRecord`，追加到输出日志文件中。
4. **条件检查**：
   - 如果动作是 `edit`，必须提供 `--edited-text`。
   - 如果动作是 `boundary`，至少提供 `--boundary-label` 或 `--boundary-note` 之一。
5. **安全输出**：返回给 CLI 的信息只包含安全的摘要字段（ID、排名、动作、记录总数、输出路径），不包含草稿文本、编辑文本或私密笔记。

#### 2.3 CLI 命令 (`src/practical_chat_agent/app/main.py`)

新增 `chat-reply-feedback` 命令，参数包括：
- `--plan`：输入的 ReplyPlan JSON 文件路径
- `--candidate-rank`：候选排名（1, 2, 3...）
- `--action`：反馈动作（accept/edit/reject/boundary）
- `--output`：输出反馈日志的路径
- `--note`、`--edited-text`、`--boundary-label`、`--boundary-note`：可选的补充信息

#### 2.4 文档更新 (`docs/07_handoff.md`)

追加了 T140 的实现记录，包括文件变更、功能描述、验证结果、剩余风险和明确声明"未做什么"。

### 验证过程

Worker 使用了一个合成的（不是真实聊天数据的）ReplyPlan 作为测试输入，依次验证了：
- 四种动作（accept/edit/reject/boundary）都能正确追加记录
- 无效的候选排名（如99）会被拒绝并提示有效范围
- `edit` 动作缺少编辑文本会被拒绝
- `boundary` 动作缺少标签和备注会被拒绝
- 命令行输出不包含草稿文本、编辑文本、私密笔记或原始聊天内容
- 输出只在用户指定的私有路径下
- 没有修改任何联系人画像、记忆库或已审批的存储记录

### 对后续开发的意义

这个任务为后续的反馈闭环奠定了基础：

- **T141**（反馈日志验证器）：可以验证 T140 产出的日志是否完整、格式是否正确
- **T142**（反馈摘要导出器）：可以汇总多条反馈，生成统计报告
- **T150/T152**（回归测试）：需要为 T140 的 schema、service 和 CLI 补充自动化测试
- **T160+**（反馈到补丁）：多条相似反馈可以被聚类，生成偏好/边界更新提案

这些后续任务都不会自动修改联系人画像或记忆库——所有变更都需要经过人工审批。这符合项目一贯的"review-first"原则。

## 3. 为什么给出 PASS_WITH_WARNINGS？

### 通过的原因

1. **任务目标完全达成**：schema 定义清晰、service 逻辑正确、CLI 可用、四种反馈动作都能正确工作。
2. **没有越界**：严格在 `Allowed files` 范围内修改，没有碰任何被禁止的东西（没有自动发送、没有修改记忆库、没有接入数据库或向量数据库、没有调用 LLM）。
3. **没有伪实现**：所有逻辑都是真实的——加载真实文件、校验真实数据、写入真实日志。没有 mock 或 stub。
4. **隐私安全**：命令行输出只包含安全的摘要信息，不会打印草稿文本、编辑内容或私密笔记。
5. **文档诚实**：handoff 文档如实记录了实现内容、验证结果和剩余风险，没有把计划写成事实。

### 警告的原因

虽然实现是正确的，但有几个值得注意但不需要返工的小问题：

1. **损坏日志的静默处理**：如果日志文件被意外损坏，程序会静默地用一个空日志覆盖它，丢失之前所有记录。应该至少给用户一个警告。但对于单用户离线工具，风险很低。
2. **路径引用可能失效**：日志中存储了回复计划文件的路径作为字符串。如果文件后来被移动，这个引用就失效了。
3. **没有路径限制**：CLI 接受任意输出路径，不强制要求在 `private/` 下。用户可能不小心写到非私有位置。
4. **缺少自动化测试**：和项目其他任务一样，测试被推迟到 T150/T152。这在项目当前阶段是可接受的惯例。

这些警告都不影响功能的正确性和安全性，所以不需要阻塞任务完成（BLOCK），但后续任务应该逐步解决。
