# T192 Review Explained: RelationshipDeltaCandidate

## 1. 这个任务在做什么？（通俗解释）

想象你和一个人（比如微信好友）的关系可以用多个维度来描述：熟悉程度、信任度、亲密度、边界风险、主动性允许度等等。T190 定义了这些维度的数据结构（`RelationshipState`），T191 做了一件很保守的事——从用户的反馈中提取出"关系信号"（比如用户说"太亲密了"，就产生一个"边界风险升高"的信号）。

T192 做的事情是：**把这些信号转化为具体的"修改建议"**。

举个例子：如果 T191 提取了一个信号说"边界风险应该升高，强度 0.7"，而当前状态中边界风险是 0.3，那么 T192 会生成一个候选修改建议（`RelationshipDeltaCandidate`），建议把边界风险从 0.3 调到 0.44（0.3 + 0.7 × 0.2 的缩放因子）。

关键设计原则是：**只生成建议，不自动执行**。每一个修改建议都需要人工审核后才能生效。

## 2. 实现细节

### 任务目标

将 T191 产生的关系信号（`RelationshipSignal`）转化为可审核的关系变更候选（`RelationshipDeltaCandidate`），并且：

- 不自动批准或应用变更
- 不修改现有的 `RelationshipState`
- 对模糊或证据不足的信号保持保守（跳过而非强行生成）

### 代码变化

#### `src/practical_chat_agent/services/feedback.py`（新增约 125 行）

新增 `RelationshipDeltaGenerator` 类，核心方法 `generate_from_signals()` 的处理流程：

1. **按联系人过滤**：只处理与当前状态 `contact_id` 匹配的信号。
2. **按维度分组**：将信号按 `dimension_name`（如 boundary_risk、intimacy_level）分组。
3. **方向一致性检查**：同一维度下所有信号必须方向一致（全是"升高"或全是"降低"）。如果出现矛盾方向、全是"未知"或全是"稳定"的情况，则跳过该维度。
4. **强度阈值过滤**：最大信号强度低于 0.3 的维度被跳过。
5. **计算提议值**：用最大信号强度 × 0.2 的缩放因子计算变化量，加到当前值上，并夹紧到 [0.0, 1.0] 范围内。
6. **重新计算幅度和方向**：不直接信任信号的强度和方向，而是从实际的 `proposed_value - current_value` 重新推导。这确保了幅度和方向的一致性。
7. **边界保护**：如果夹紧后幅度接近零（< 1e-6），说明已经在边界上无法再变，直接跳过。
8. **证据引用**：收集所有信号带来的 `evidence_refs` 并去重，但不包含状态自身的证据引用。
9. **信号引用**：收集所有参与信号的 `signal_id`。

设计上的保守性体现在：
- 模糊/矛盾信号 → 不生成变更
- 弱信号（强度 < 0.3） → 不生成变更
- 已经在边界上 → 不生成变更
- 所有生成的变更都是 `status="candidate"`，需要人工审核

#### `tests/test_relationship_deltas.py`（新文件，26 个测试）

测试覆盖了：

- **正常路径**：边界违规、过度亲密、过度热情三种信号模式都能正确生成变更。
- **空路径**：空信号、错误联系人、未知方向、弱信号、矛盾方向、稳定方向 → 都不生成变更。
- **幅度/方向一致性**：幅度 = |提议值 - 当前值|，方向从实际值推导，上下界夹紧正确。
- **证据保留**：信号证据正确传递和去重，状态证据不混入。
- **状态不可变性**：生成器不修改传入的状态对象。
- **候选属性**：状态始终是 "candidate"，理由非空，无原始文本泄露。
- **多信号聚合**：同维度多信号用最大强度，所有信号 ID 都被收集。

### 对后续开发的意义

T192 是 M8（RelationshipState 里程碑）的中间环节：

```
T190（定义维度和变更模式）
  → T191（从反馈中提取信号）
  → T192（将信号转化为变更建议）  ← 当前任务
  → T193（人工审核变更建议的 CLI）
  → T194（将审核通过的关系状态注入回复上下文）
  → T195（关系感知回复评估）
```

T192 建立了信号到变更建议的桥梁。它确保了：

1. **审计链完整**：每个变更建议都追溯到具体的信号和证据。
2. **人类在环**：变更不会自动生效，T193 将提供人工审核界面。
3. **保守策略**：宁可漏掉一个合理的变更，也不生成一个有风险的变更。

### 配置文件变化

`.claude/settings.json` 中新增了 T192 验证命令的权限条目，这与之前所有任务（T160-T191）的模式一致，是工作区配置产物而非任务范围违规。

## 3. 为什么给出 PASS_WITH_WARNINGS？

### 做得好的地方

1. **实现简洁且保守**：约 125 行代码完成核心逻辑，没有过度工程。
2. **幅度重新计算**：不信任信号强度，而是从 `abs(proposed - current)` 重新推导，这是一道重要的安全防线。
3. **方向验证**：同样不信任信号方向，从实际值对比推导。
4. **测试全面**：26 个测试覆盖了正常路径、空路径、边界情况、不可变性和无泄漏。
5. **无范围越界**：没有自动批准、状态变更、发送逻辑或 LLM 调用。
6. **文档同步**：数据合约和 handoff 都更新了。
7. **零回归**：全部 488 个测试通过。

### Warnings 的原因

1. **N01: 缩放因子 0.2 和最低强度 0.3 是未经验证的启发值**：这些数值没有经过真实数据校准。但因为所有变更都需要人工审核，这个风险在当前阶段是可控的。
2. **N02: 最大强度聚合丢失了信号数量信息**：如果 5 个弱信号都指向同一方向，它们不会比 1 个强信号产生更大的影响。这在保守框架下是可接受的，但未来可能需要改进。
3. **M01: 缺少维度不在状态快照中的测试**：如果信号引用了一个不存在的维度名称，代码正确地跳过了它，但没有测试证明这一点。
4. **M02: 缺少已知方向 + 未知方向混合的测试**：当同一维度有 1 个 `increase` + 2 个 `unknown` 信号时，应该生成变更，但没有显式测试。

这些 warnings 不影响 T192 的核心功能正确性，且风险已被保守的设计（候选状态 + 人工审核）所缓解。
