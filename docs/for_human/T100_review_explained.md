# T100 任务与 Review 通俗解释

更新日期：2026-05-14

## 一、这个任务在做什么（通俗版）

### 背景一句话

你用 WeFlow 工具把微信聊天记录导出成了一堆文件（就像把微信聊天记录"另存为"到电脑上）。但在用这些记录做任何事之前，我们需要先搞清楚：**这些文件里到底长什么样？有哪些字段？有没有隐私风险？**

### 为什么需要这个任务

想象你收到一个密封的快递箱，里面装了你过去几个月的微信聊天记录。你不能直接把整个箱子交给一个 AI 去分析——因为里面有你朋友的真实姓名、手机号、私人对话内容。

正确的做法是：**先戴上手套（隐私保护），打开箱子（读取文件），只记录"这个箱子里有多少东西、每样东西是什么形状"（字段统计），然后关上箱子。全程不拍照、不抄原文、不记真名。**

T100 就是"打开箱子、画结构图、确认隐私边界"这一步。

### 具体做了什么

1. **数了数文件**：`private/chat_history/` 里有 4 个 WeFlow 导出的 JSONL 文件，总共 38,289 行，全部能正常解析（没有坏行）。

2. **给文件起了假名**：真实文件名包含联系人姓名（比如"私聊_某某.jsonl"），所有文档里一律用 `file_01` 到 `file_04` 代替。

3. **画了结构图**：发现每一行 JSON 都是以下三种类型之一：
   - `header`：文件头，记录导出工具信息和会话元数据（每个文件 1 行）
   - `member`：成员信息，包含平台 ID 和展示名（共 32 行）
   - `message`：实际聊天消息（共 38,253 行，占 99.9%）

4. **分析了消息类型**：消息有个 `type` 字段，发现主要有 8 种编码。最多的是 `type=0`（普通文本，占 72.75%），其次是 `type=7`（混合内容，可能含图片/链接等，占 13.98%）、`type=25`（回复消息，占 12.48%）和 `type=80`（系统消息如撤回/红包等，占 0.69%）。

5. **确认了时间格式**：时间戳是标准的 Unix 时间（从 1970 年 1 月 1 日至今的秒数），范围从 2025 年 11 月到 2026 年 5 月。但没有时区信息，需要后续约定。

6. **找到了判断"谁发的"的方法**：通过"跨文件出现的成员"来识别哪个是你（本地用户），哪个是对方（联系人）。

7. **建立了数据合约**：规定了如何把 WeFlow 的原始数据转换成统一的 normalized event 格式——包括事件 ID 怎么生成、发送者角色怎么判断、消息类型怎么映射等。

8. **做了一个假的示例文件**：5 行完全合成的 JSONL 数据，能代表真实结构但不包含任何真实内容。

### 打个比方

这就像你要整理一个巨大的图书馆：

- **T100 做的事**：数了有多少本书 → 给每本书编了号（不写真实书名）→ 画了"每种书长什么样"的示意图 → 建了"以后怎么统一编目"的规则手册
- **还没做的事**：把书分类上架、写摘要、提取知识点——这些留给后面的任务

## 二、任务的详细技术解释

### 2.1 任务目标

T100 的正式目标是：**读取 `private/chat_history/` 中的 WeFlow JSONL 导出，建立字段结构画像和 normalized event 合约，不泄露聊天原文或真实联系人标识。**

这来自项目实验计划（`docs/02_experiment_plan.md`）的 Milestone 0 阶段。整体项目规划了 6 个 Milestone（M0 到 M5），从"搞清数据长什么样"一直到"评估与工程硬化"。T100 是 M0 的第一步，也是整个离线蒸馏管线的地基。

### 2.2 任务流程

```
读取 private/chat_history/ 的 4 个 JSONL 文件
  ↓
统计：文件数量、总行数、可解析行数、失败行数
  ↓
分类：header / member / message 三种行类型
  ↓
分析 message 行的字段结构、类型分布、出现率
  ↓
识别消息类型候选（type 字段的 8 种编码）
  ↓
确认时间戳格式（Unix epoch seconds）
  ↓
建立发送者/方向判定规则（跨文件复用身份）
  ↓
识别隐私风险字段（11 个字段需脱敏）
  ↓
起草 normalized event 合约（schema + ID 生成 + 映射规则）
  ↓
生成合成脱敏样例（5 行 JSONL）
  ↓
更新 handoff 和 risks 文档
```

### 2.3 代码变化/配置变化

本次任务**没有修改任何源代码**，只产生了文档和样例文件。这是刻意为之的——T100 的任务包明确禁止修改 `src/practical_chat_agent/**`。

| 文件 | 变化类型 | 说明 |
| --- | --- | --- |
| `docs/data_contracts/weflow_schema_profile.md` | 新增 | WeFlow 数据结构画像：字段统计、消息类型分布、时间戳格式、方向判定、隐私风险清单 |
| `docs/data_contracts/normalized_event_contract.md` | 新增 | 归一化事件合约：JSON schema 草案、ID 生成规则、映射规则、脱敏原则 |
| `examples/payloads/weflow_redacted_sample.jsonl` | 新增 | 5 行纯合成 JSONL 样例，覆盖 header/member/message/reply 结构 |
| `docs/07_handoff.md` | 修改 | 状态从"ready for worker"更新为"worker 交付已出，待 review" |
| `docs/08_risks_and_open_questions.md` | 修改 | 新增 R010（member 行过多风险），关闭 Q100/Q104，更新 Q101-Q103 的解决时间点 |

**没有变化的**：
- `src/practical_chat_agent/**` — 主仓库业务代码完全没动
- `docs/04_task_board.md` — 任务板没动（按规定只能由 Captain 更新）
- `private/chat_history/**` — 原始数据只读不写

### 2.4 对后续开发的意义

T100 看起来只是"看了看文件长什么样"，但它为后续所有任务奠定了数据基础：

1. **确认了数据可解析性**：38,289 行全部能解析，0 坏行。这意味着后续的 adapter（T102）可以安全地假设输入是合法 JSON，不需要处理大量格式异常。

2. **建立了字段到用途的映射**：
   - `type` → 消息类型（text/reply/system/mixed/unknown）
   - `timestamp` → 时间（epoch seconds，需配置时区）
   - `sender` + `accountName` → 发送者身份
   - `replyToMessageId` → 引用链
   - `chatRecords` → 转发记录
   - `platformMessageId` → 唯一消息标识

3. **提供了方向判定的可行方案**：通过"跨文件复用的成员对"识别本地用户，这比简单比较 `sender == accountName` 更可靠（实际上这两个字段是不同身份槽位）。

4. **划定了隐私红线**：明确了 11 个字段不能以明文进入可提交产物，为 T101（正式脱敏规则）和 T150（隐私泄露测试）提供了检查清单。

5. **暴露了已知不确定性**：`type=7` 混合了多种内容（图片、链接、转发记录等），`file_04` 虽然是私聊但 member 行异常多，稀有 type 编码的语义不明。这些不是 bug，而是被正确记录为"后续需要解决的问题"。

6. **项目路线图定位**：根据 `04_task_board.md`，当前处于 Milestone 0（WeFlow 数据合约与隐私护栏）。T100 完成后，依次是 T101（脱敏规则和红线测试）→ T102（最小 normalize CLI）→ T103（M0 review）。只有通过 M0 review，才会进入 M1（离线蒸馏 MVP）。

## 三、为什么 Reviewer 给出了 PASS

### 3.1 Review 做了什么

Reviewer 的工作是"独立检查 worker 的活儿干得好不好"，具体做了以下检查：

1. **读了任务包**：确认 T100 要求做什么、禁止做什么
2. **看了所有改动**：检查 worker 是否只改了允许的 5 个文件
3. **独立验证了关键声明**：重新解析了样例 JSONL、搜索了真实文件名泄露
4. **检查了隐私安全**：获取了 `private/chat_history/` 的真实文件名列表，逐一比对交付文件
5. **检查了文档质量**：看有没有把没做的事写成做了

### 3.2 PASS 的核心理由

| 检查维度 | 结论 | 说明 |
| --- | --- | --- |
| **是否完成任务** | 是 | 任务包列出的 16 项具体要求全部完成 |
| **是否越界** | 没越界 | 只改了允许的 5 个文件，没碰源代码和任务板 |
| **隐私是否安全** | 安全 | 真实文件名（含联系人姓名）在交付文件中零出现；样例全部是合成内容 |
| **有没有造假** | 没有 | 统计数据来自真实分析（38,289 行全部可解析）；映射建议标注为"候选"而非定论 |
| **是否过早宣称完成** | 没有 | handoff 明确写"待 review"；risks 中关闭的问题标注为"worker draft" |
| **有没有过度工程** | 没有 | 只做了必要的结构分析和合约草案，没有提前写 adapter 代码 |
| **是否破坏已有功能** | 没有 | 主仓库零代码变更 |

### 3.3 三个小提醒（Non-blocking Issues）

Reviewer 发现了三个不阻碍通过但值得注意的点：

1. **Q100/Q104 的关闭依据是 "worker draft"**：这两个问题被移到了"已关闭"列表，但依据是 worker 自己的草稿而不是 review 结论。Reviewer 认为这两条的结论是正确的（本次 review 已验证），所以不阻断。建议 Captain 更新一下依据。

2. **样例 fixture 没有覆盖系统消息和转发记录**：5 行样例覆盖了 header、member、普通文本和回复消息，但没有 type=80（系统消息）和 chatRecords（转发记录）的合成行。这不违反 T100 的要求，但后续 T102/T150 可能需要补充。

3. **event_id 用了 SHA-1 哈希**：SHA-1 在密码学意义上已不安全，但这里只是用来生成稳定别名，输入空间极小，碰撞概率可忽略。可接受，无需更改。

这三个提醒都不影响 T100 的通过判定。

Reviewer 建议：
1. Captain 把 T100 标记为完成
2. 推进 T101（设计脱敏规则、source_ref 规则和最小红线测试样例）或 T102（实现 WeFlow adapter 的最小 normalize CLI）
3. T102 在实现 adapter 时参考 N02，补充更多消息类型的合成 fixture
