# T133 Review Explained: Holdout Eval（Holdout 评估里程碑）

## 一、这个 Task 在做什么？（通俗解释）

T131 做了一个回复草稿生成器，T132 给它加了安全检查层。现在到了一个关键问题：**这套东西到底好不好用？**

T133 就是对 T130-T132 整个回复规划管线做一次"期中考试"。

具体来说，它设计了 6 道题：

| 编号 | 场景 | 考什么 |
|---|---|---|
| H01 | 普通朋友闲聊 | 基本功能能不能跑通 |
| H02 | 工作同事沟通 | 务实场景下是否合适 |
| H03 | 对方提到敏感话题 | 系统能不能识别并变保守 |
| H04 | 对这位联系人了解很少 | 信息不足时是否谨慎 |
| H05 | 普通对话但可能被误判为敏感 | 会不会过度紧张（误报） |
| H06 | 真的有微妙风险但不太明显 | 会不会漏掉（漏报） |

每道题都是**合成/匿名化的假数据**——不包含任何真实的聊天记录或联系人信息。系统对这 6 个场景各生成一套回复草稿，然后评估：
- 结构是否正确（有没有 3 个候选、ID 是否对齐）
- 回复是否自然
- 是否遵守了边界规则
- 有没有隐私泄漏

**重要定位**：T133 是一个**只产出文档和私有评估产物**的任务。它不改任何代码，只做评估和记录。

## 二、实现详解

### 2.1 任务目标

T133 的目标是以 Milestone Review（里程碑评审）的形式评估 M3 阶段（T130-T132）的完成度，回答三个关键问题：

1. ReplyPlanner 在当前环境下能不能跑？（功能性）
2. 边界检测做得好不好？（安全性）
3. M3 阶段能不能放行到 M4？（里程碑门控）

### 2.2 任务流程

```
准备阶段
  ├─ 设计 6 个合成匿名化场景（H01-H06）
  ├─ 为每个场景构建 .context.json（ChatContext 格式，全部使用假 ID）
  │
评估阶段
  ├─ 对每个场景运行 chat-reply-plan CLI 生成 .reply_plan.json
  ├─ 检查每个 plan 的结构完整性（3 候选、ID 对齐、引用来源）
  ├─ 评估回复自然度（naturalness_rating）
  ├─ 评估边界遵守（boundary_adherence_rating）
  ├─ 评估证据引用质量（evidence_usage_rating）
  │
  ├─ 专门检查 H05（误报）：普通对话是否被误判为敏感
  ├─ 专门检查 H06（漏报）：微妙风险是否被忽视
  │
产出阶段
  ├─ eval_summary.json（私有评估汇总）
  ├─ T133_milestone_review.md（里程碑评审文档）
  ├─ docs/07_handoff.md Section 29（交接记录）
  └─ Gate M3 判定：Conditional（有条件通过）
```

### 2.3 评估结果

| 指标 | 结果 | 含义 |
|---|---|---|
| 有效计划生成率 | 6/6 | 所有场景都能正常运行 |
| 候选数量正确率 | 6/6 | 每个 plan 都有 3 个候选 |
| 回复自然度 | 3/5 | 及格但不出色（模板驱动） |
| 边界遵守 | 4/5 | 表现不错 |
| 证据引用质量 | 3/5 | 引用结构正确但内容偏浅 |
| 隐私泄漏 | 0 | 提交文件中没有泄漏 |

### 2.4 对后续开发的意义

T133 在整个项目路线图中的位置：

```
M3: 回复规划
  T130: 定义 ReplyPlan schema     ✅
  T131: 实现 ReplyPlanner          ✅
  T132: 增加策略安全层              ✅
  T133: Holdout 评估               ✅ ← 我们在这里
                                      │
                                      ▼ Gate M3 = Conditional
M4: 反馈闭环                         │（满足 3 个条件才能进入）
```

**T133 的意义**：

1. **确认了管线在结构上是完整可运行的**。6 个场景、6 次成功生成，说明 T130 的 schema、T131 的 planner、T132 的 policy 引擎组合在一起不会崩溃。

2. **诚实地报告了质量限制**。自然度 3/5 不是掩饰的高分，而是坦率地说"模板驱动，关系感知偏浅"。这种诚实评估比虚假的高分更有价值。

3. **发现了误报和漏报问题**。H05 证明普通工作场景有时会被误判为敏感；H06 证明某些微妙的风险线索可能被忽视。这给 T150（自动化回归测试）提供了明确的测试用例方向。

4. **Gate M3 = Conditional 而不是 Allow**。这意味着 M4 可以开始，但必须带着三个条件：保持 review-only、T150 补测试、不能宣称"关系感知已成熟"。

## 三、为什么我给出了 PASS_WITH_WARNINGS 的 Review 结果？

### 通过（PASS）的部分

1. **任务包要求全部满足**：只有文档和私有产物被修改，没有改 `src/**` 代码。

2. **隐私保护到位**：抽查了 H03 的 context 和 plan 文件，所有 ID 都是合成的（"holdout_sensitive"、"Anon Contact"），敏感文本用 "??" 替代。提交的 diff 中没有真实的聊天记录、联系人名称或平台 ID。

3. **评估方法设计合理**：6 个场景覆盖了关键维度——基线、工作、敏感、薄上下文、误报探针、漏报探针。既有正向路径也有边缘案例。

4. **H03 展示了正确的保守行为**：
   - 草稿措辞变为保守风格（"你不用现在展开"）
   - 所有候选都标记了 `boundary_sensitive`
   - 候选 2 被额外标记为 `over_proactive`（因为它包含可选追问）
   - 置信度从基线的 0.78/0.71/0.66 降到 0.72/0.57/0.60

5. **评分没有注水**：自然度 3/5、边界 4/5、证据 3/5。Worker 自己指出了"整体还是模板驱动，关系感知偏浅"，而不是回避这个限制。

6. **Gate M3 判定适当保守**：`Conditional` 而不是 `Allow`，附带 3 个明确可执行的条件。

### 带有 Warning 的部分

Warning 1：**评分是自报的，没有独立验证。**
- 3/5、4/5、3/5 是 worker 自己给自己的打分
- 没有独立的人类评审员或评分者间一致性
- **为什么不是 BLOCK**：T133 是文档评估任务，评分是结构化自评而非统计声明。条件 2 明确将进一步验证推迟到 T150。

Warning 2：**样本量只有 6 个，全部是合成数据。**
- 没有使用 `private/chat_history/` 下的真实 holdout 数据（任务限制不允许）
- 评估证明了管道接线和安全行为正确，但不能证明真实世界的自然度
- **为什么不是 BLOCK**：任务明确限制为"synthetic or redacted input"。6 个场景覆盖关键维度，对里程碑门控来说合理。

Warning 3：**自然度 3/5 勉强及格。**
- 意味着草稿"可接受但不令人印象深刻"
- 结合模板驱动的特点，生成的是安全但通用的回复
- **为什么不是 BLOCK**：里程碑评审正确识别了这个限制，条件 3 要求在更广样本上重新校准后才能宣称成熟。

Warning 4：**基线场景（H01、H02）的具体发现未被记录。**
- 评审文档详细讨论了 H03-H06，但 H01 和 H02 只被确认"成功"，没有具体的匿名化发现
- **为什么不是 BLOCK**：`eval_summary.json` 确认全部 6 个场景都成功生成了有效 plan。基线场景没有异常值得报告。

### 总结

T133 是一个结构良好的里程碑评估。它用 6 个合成匿名化场景验证了 T130-T132 的回复规划管线在结构上完整、在安全行为上正确，同时诚实地报告了质量限制（模板驱动、自然度 3/5、关键词策略的误报/漏报）。Gate M3 的 `Conditional` 判定是适当的保守选择——管线可以继续，但不能宣称成熟。
