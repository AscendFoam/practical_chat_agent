## 一、这个任务在做什么（通俗版）

### 背景一句话

T00 确认了"微信连接工具能装上、能启动到扫码界面"。但扫码之后会怎样？登录信息能不能保存？关掉再开还要重新扫码吗？这些都不知道。**T01 就是来回答这些问题的。**

### 打个比方

如果说 T00 是"网购了一个新电器，拆快递、插电、确认指示灯能亮"，那 T01 就是：

1. **真正按一下开关**：用手机扫一下二维码，看电器能不能连上网
2. **拔掉电源再插上**：看它记不记得之前的网络设置，还是每次都要重新配置
3. **看看电池能用多久**：登录状态能维持多久？过期了会怎样？

### 具体要验证什么

| 验证项 | 通俗解释 | 为什么重要 |
| --- | --- | --- |
| 扫码登录 | 二维码扫了之后，SDK 能不能成功连接微信 | 这是所有后续功能的基础——连不上就啥也干不了 |
| 凭据缓存 | 登录成功后，SDK 会不会把登录信息存到本地文件 | 如果不存，每次重启都要重新扫码，非常麻烦 |
| 重启恢复 | 关掉程序再开，能不能自动用之前存的凭据重新连上 | 决定了程序能不能长期稳定运行 |
| 会话失效 | 登录状态过期了会怎样？有没有自动重登能力 | 决定了程序能不能自动恢复，还是需要人工介入 |

### 当前进展到哪里了

Worker 写了一个很不错的登录测试脚本（`t01_login_probe.py`），成功生成了二维码图片。**但二维码生成后，没有人扫码确认，二维码过期了 3 次，SDK 自动中止了。**

也就是说：二维码准备好了，但"真正按一下开关"这一步还没完成。

## 二、任务的详细技术解释

### 2.1 任务目标

T01 的正式目标是：**验证 sandbox 中 SDK 的扫码登录、凭据缓存、重启恢复、登出/过期和自动重登行为。**

这是 Milestone 0（WeChatBot/iLink 隔离 POC）的第二步任务。整个 Milestone 0 的目标是回答一个关键问题：**"WeChatBot SDK 值不值得接入到主项目中？"**

T01 在这个决策链中的位置：

```
T00：SDK 能不能装上、能不能启动？  ✅ 已通过
  ↓
T01：能不能登录？登录状态能不能保持？  ❌ 当前卡在这里
  ↓
T02：能不能收到消息？消息里有什么字段？  ⏳ 等待 T01
  ↓
T03：能不能发消息？媒体能不能处理？  ⏳ 等待 T02
  ↓
T04：综合评估，决定是否进入主仓库  ⏳ 等待 T03
```

### 2.2 任务流程

Worker 实际执行的流程：

```
1. 阅读 T00 review 结论和 T01 任务包
   ↓
2. 检查 sandbox 当前状态（是否有已有凭据）
   ↓
3. 阅读 SDK 源码（client.py, auth.py）
   → 发现：默认凭据文件名是 credentials.json
   → 发现：start() 遇到 session expired 会清理凭据再重新登录
   ↓
4. 编写登录探针脚本 t01_login_probe.py
   → 支持回调：二维码生成、已扫码、过期、错误
   → 状态持久化到 JSON 文件
   → 二维码保存为图片
   → 登录成功时记录脱敏后的账号信息
   ↓
5. 运行探针
   → 二维码成功生成（t01_qr.png, 1362 bytes）
   → 等待扫码...
   → 无人扫码，二维码过期
   → 重新生成二维码...
   → 仍然无人扫码
   → 3 次过期后，SDK 抛出 AuthError，探针退出
   ↓
6. 【未完成】等待用户配合扫码
```

### 2.4 探针脚本的技术亮点

Worker 在执行前先读了 SDK 源码，理解了以下关键行为，然后才写脚本：

1. **凭据文件**：SDK 默认使用构造函数中 `cred_path` 参数指定的文件路径
2. **自动重登**：`start()` 方法在检测到 session expired 时会清理凭据并重新走登录流程
3. **QR 过期机制**：SDK 内部有 QR 过期重试逻辑（3 次后中止）

探针脚本的设计：
- 使用 `force=True` 强制重新登录（而非复用已有凭据）
- 通过回调函数追踪登录流程的每个阶段
- 状态写入 JSON 文件，方便后续分析
- 登录成功后只记录账号 ID 的后 6 位（脱敏处理）

### 2.5 对后续开发的意义

T01 是 Gate 0 决策的关键输入之一。它的结果直接影响：

1. **T02（收消息验证）**：如果登录不稳定或凭据无法恢复，收消息测试就无法进行
2. **主仓库接入设计**：如果 SDK 的登录/会话行为已知，M1 中的 `WeChatIlinkSession` 服务可以准确设计凭据管理、自动重登和状态恢复逻辑
3. **风险评估**：如果登录经常失效或恢复机制不可靠，`docs/08_risks_and_open_questions.md` 中的 R001（SDK 无法稳定登录）就需要升级

根据 `02_experiment_plan.md` 的 Sprint 5.5（回滚与停止条件），如果"无法稳定扫码登录"，应暂停 iLink 主线。因此 T01 的结论直接关系到整个微信主线是否继续推进。

## 三、为什么 Reviewer 给出了 BLOCK

### 3.1 核心原因：任务没有完成

Reviewer 的职责是检查"worker 有没有完成 T01 任务包要求的所有验证"。逐项检查：

| 任务包验证要求 | 是否完成 | 说明 |
| --- | --- | --- |
| 完成至少一次登录 | **没有** | QR 码过期 3 次，SDK 抛出 `AuthError` |
| 关闭并重启脚本，观察是否复用凭据 | **没有** | 登录都没成功，无法测试重启 |
| 记录失败时的错误摘要 | **部分** | 状态文件有记录，但没有写入 POC notes |
| 明确记录测试账号类型 | **没有** | 没有任何文档记录 |
| Python 版本兼容风险 | **没有** | T00 遗留的 N01 问题未在文档中回应 |
| 官方文档 URL 对应关系 | **没有** | T00 遗留的 N02 问题未在文档中回应 |

**5.5 项验证要求中，0.5 项有部分进展，其余全部未完成。** 因此无法给出 PASS。

### 3.2 Worker 做对了什么

BLOCK 不代表 Worker 做得差。实际上 Worker 的方法论是正确的：

1. **先读源码再动手**：Worker 在测试前先读了 `client.py` 和 `auth.py`，理解了凭据和重登机制
2. **探针脚本质量好**：回调完整、状态追踪清晰、脱敏处理合理、不过度工程
3. **没有越界**：没有修改主仓库业务代码
4. **没有伪造结果**：状态文件如实记录了失败

### 3.3 为什么卡住了

T01 卡在"需要人工配合扫码"这个环节：

- Worker 生成了二维码，发出了"请扫码"的请求
- 但 QR 码有时效性（通常 2-3 分钟），且 SDK 只允许过期 3 次就中止
- 在无人扫码的情况下，探针已经自动退出

这是一个**执行层面的阻塞**，不是方法论问题。Worker 需要用户在场时重新运行探针并即时扫码。

### 3.4 一个小问题：`.gitignore` 越界

Worker 在主仓库的 `.gitignore` 中新增了 `private/`。这不在 T01 的 Allowed files 列表内。

虽然这个变更本身是合理的（防止私有目录被意外提交），但 reviewer 必须指出任何越界行为。这是一个 non-blocking issue，不会导致更严重的后果，但提醒 Worker 应严格遵守 Allowed files 边界。

### 3.5 下一步怎么办

1. **用户确认测试微信账号**：这是 Q002 遗留的问题
2. **用户在场时重新运行探针**：`python t01_login_probe.py`
3. **用户在 QR 码出现后 2-3 分钟内扫码确认**
4. **登录成功后继续验证**：检查 `credentials.json`、重启复用、失效表现
5. **更新文档**：把所有结果写入 POC notes、handoff 和 risks
6. **回应 T00 遗留问题**：N01（Python 版本）和 N02（文档 URL）
