## 一、这个任务在做什么（通俗版）

### 背景一句话

我们要做一个"微信智能助手"——帮你管理微信聊天、记住重要信息、建议回复内容。但在正式开工之前，我们需要先确认：**用来连接微信的工具（SDK）到底能不能用。**

### 为什么需要这个任务

想象你要盖一栋楼（微信智能助手），现在有人推荐了一种新型水泥（WeChatBot SDK）。你不能直接拿整栋楼去试这种水泥好不好用——万一不行，楼就废了。

所以正确的做法是：**先在旁边搭个小棚子（sandbox），用这种水泥试试看，确认没问题了再拿去盖楼。**

T00 就是"搭小棚子、买水泥、看看能不能和得上"这一步。

### 具体做了什么

1. **在主项目外面建了一个隔离的实验目录**（`D:\Codes\Social\wechatbot_sandbox`），这样即使实验出问题也不会影响主项目。

2. **安装了 WeChatBot SDK**（一个 Python 包，叫 `wechatbot-sdk`，版本 `0.2.1`）。这是连接微信的"工具箱"。

3. **试了一下能不能打开工具箱**：
   - `from wechatbot import WeChatBot` — 能打开 ✓
   - `WeChatBot(...)` — 工具箱能正常初始化 ✓

4. **试了一下登录入口**：
   - 调用了 SDK 的登录方法
   - SDK 弹出了二维码（就像网页版微信登录那样需要你扫码）
   - 因为是测试，没有真的扫码，只是确认"能走到扫码这一步"

5. **把所有结果老老实实记了下来**，包括成功的和还没验证的。

### 打个比方

这就像你网购了一个新电器：
- **T00 做的事**：拆快递 → 看看配件齐不齐 → 插上电源看能不能亮指示灯
- **还没做的事**：实际使用所有功能（扫码登录、收消息、发消息等），这些留给后面的任务

## 二、任务的详细技术解释

### 2.1 任务目标

T00 的正式目标是：**在主仓库外建立 WeChatBot/iLink SDK sandbox，完成安装和官方 QuickStart/最小启动验证，并记录真实结果。**

这来自项目整体实验计划（`docs/02_experiment_plan.md`）的 Sprint 0 阶段。整体项目规划了 7 个 Sprint（Sprint 0 到 Sprint 7），从"先试试 SDK 能不能用"到"最终工程化"逐步推进。T00 是 Sprint 0 的第一步，也是整个 Gate 0 决策的基础。

### 2.2 任务流程

```
阅读项目文档
  ↓
在仓库外创建隔离 sandbox（D:\Codes\Social\wechatbot_sandbox）
  ↓
创建 Python 虚拟环境（.venv）
  ↓
安装 wechatbot-sdk（pip install wechatbot-sdk）
  ↓
验证：导入是否成功？构造是否成功？
  ↓
验证：QuickStart 登录入口能否启动？
  ↓
记录所有结果到文档
  ↓
更新交接文档和风险文档
```

### 2.3 代码变化/配置变化

本次任务**没有修改任何主仓库代码**，这是刻意为之的安全措施。具体变化：

| 文件 | 变化类型 | 说明 |
| --- | --- | --- |
| `docs/wechat_ilink_poc_notes.md` | 新增 | SDK 版本、安装命令、Python 版本、导入结果、登录探测结果、确认与未确认清单 |
| `docs/07_handoff.md` | 新增 | 交接文档，说明 T00 已执行、当前证据边界、reviewer 之后的处理顺序 |
| `docs/08_risks_and_open_questions.md` | 新增 | 风险文档，补充了 R009（sandbox 环境验证范围有限）和 Q009（凭据落盘时机） |
| 仓库外 sandbox | 新增 | `D:\Codes\Social\wechatbot_sandbox` 含 Python venv 和已安装的 SDK |

**没有变化的**：
- `src/practical_chat_agent/**` — 主仓库业务代码完全没动
- `pyproject.toml` — 依赖配置没动
- `docs/04_task_board.md` — 任务板没动（按规定只能由 Captain 更新）

### 2.4 对后续开发的意义

T00 虽然看起来只是"装个包试了试"，但它为后续所有工作奠定了基础：

1. **回答了 Q001**：SDK 包名是 `wechatbot-sdk`，版本 `0.2.1`，导入路径是 `from wechatbot import WeChatBot`。后续所有任务都不需要再猜测这些信息。

2. **确认了最低可行基线**：SDK 能装、能导入、能构造、能进入登录流程。这意味着后续任务（T01 扫码登录、T02 收消息、T03 发消息）有了一个确认可用的起点。

3. **明确了边界**：记录了"还没确认什么"，让后续任务知道该优先验证什么。比如 T01 知道要优先验证凭据落盘和重启恢复。

4. **Gate 0 决策的输入**：整个 Sprint 0 的目标是通过 Gate 0——决定"要不要用这个 SDK 接入微信"。T00 是 Gate 0 的第一块拼图。

5. **项目路线图定位**：根据 `04_task_board.md`，当前处于 Milestone 0（共 8 个 Milestone，M0 到 M7），从"试试 SDK"一直到"最终工程化"。T00 是 M0 的第一步，后面依次是 T01（登录验证）→ T02（收消息验证）→ T03（发消息验证）→ T04（Gate 0 决策）。只有通过 Gate 0，才会进入 M1（把微信接入主项目代码）。

## 三、为什么 Reviewer 给出了 PASS

### 3.1 Review 做了什么

Reviewer 的工作是"独立检查 worker 的活儿干得好不好"，具体做了：

1. **读了任务包**：确认 T00 允许做什么、禁止做什么
2. **看了所有改动**：检查 worker 是否只改了允许的文件
3. **独立重跑了关键命令**：确认 worker 报告的结果是真的
4. **检查文档质量**：看有没有把没做的事写成做了

### 3.2 PASS 的核心理由

| 检查维度 | 结论 | 说明 |
| --- | --- | --- |
| **是否完成任务** | ✓ 是 | 任务要求"安装 SDK + 验证 QuickStart + 记录结果"，都做了 |
| **是否越界** | ✓ 没越界 | 只改了允许的 3 个文档文件，没碰主代码、没改任务板 |
| **结果是否真实** | ✓ 是真实的 | Reviewer 独立重跑了安装、导入、构造命令，结果一致 |
| **有没有造假** | ✓ 没有 | 所有记录可复现，没有 mock/stub/假数据 |
| **是否过早宣称完成** | ✓ 没有 | 文档明确区分"已确认"和"仍未确认"，明确说"不要把 Gate 0 视为通过" |
| **有没有过度工程** | ✓ 没有 | 只写了必要的实验记录，没有提前设计架构或写脚手架 |
| **是否破坏已有功能** | ✓ 没有 | 主仓库零代码变更 |

### 3.3 两个小提醒（Non-blocking Issues）

Reviewer 发现了两个不阻碍通过但值得注意的点：

1. **Python 版本偏差**：项目计划提到 Python 3.11，但实际 sandbox 用的 3.12.7。目前不影响结论，但后续接入主仓库时需要确认版本兼容性。
2. **官方文档 URL 未独立验证**：POC 记录引用了一个文档网址，Reviewer 没去验证它是否能打开。不影响本地实验结果的真实性，但后续任务可以顺便确认。

这两个提醒不影响 T00 的通过判定，可以留给后续任务顺带处理。
