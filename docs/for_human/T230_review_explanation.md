# T230 WeChat Adapter Research Spike - 解释文档

## 一、这个任务在做什么（通俗解释）

这个项目正在构建一个"关系感知聊天助手"——它能帮你分析聊天记录、了解你和联系人的关系状态、然后帮你起草回复消息。

到了 M11 阶段，项目已经建好了一套"发送安全边界"：
- 你想发消息时，系统先生成一个 `OutboundMessageRequest`（发送请求）
- 然后经过 `OutboundSendGate`（发送闸门）检查——是否有人工审批、是否在安静时间、频率是否过高等
- 目前只有两个"适配器"：一个本地假适配器（假装发送成功）和一个飞书沙箱适配器（构造飞书格式但不真发）

现在的问题是：**能不能给微信也做一个适配器？**

T230 不是去实现微信适配器，而是一个"调研刺探"任务——就像在盖房子之前先勘测地质一样，先搞清楚：

1. 微信家族有哪些可能的接入方式（个人微信、企业微信、公众号、小程序客服等）？
2. 每种方式需要什么条件（企业认证、开发者账号、回调服务器等）？
3. 哪些是官方支持的、哪些是不安全的野路子？
4. 这些方式能不能满足项目已有的安全要求（必须人工审批、不能自动发送、必须记录审计日志等）？
5. 如果搞不了微信，是不是继续用飞书/手动复制就好？

## 二、任务实现详解

### 任务目标

产出一个纯文档的研究报告，决定 M12 里程碑是否可以安全推进任何微信适配器路径。**不允许写任何代码。**

### 任务流程

1. **审阅现有架构**：Worker 阅读了项目的核心模型（`OutboundMessageRequest`、`OutboundSendGate`）、飞书适配器（`feishu_review_card.py`）和数据合约文档，理解了 M11 已建立的安全边界。

2. **调研微信家族平台**：Worker 查阅了微信/企业微信官方开发者文档（共 9 个官方文档链接），逐一分析了以下 7 种候选方案：

   | 方案 | 结论 |
   |------|------|
   | 个人微信好友聊天 | **阻止**：没有官方 API，任何实现都会涉及扫码、Hook、逆向等不安全手段 |
   | 企业微信内部应用消息 | **有条件允许**：官方 API，但需要企业租户和自建应用 |
   | 企业微信客服消息 | **有条件允许**：官方 API，有 48 小时服务窗口限制，是最有潜力的官方方案 |
   | 公众号客服消息 | **有条件允许**：官方 API，但仅限公众号订阅者 |
   | 小程序客服消息 | **推迟**：仅适用于小程序场景 |
   | 桌面自动化/手动复制 | **允许手动复制**（人类操作），阻止桌面自动化 |
   | 继续飞书/手动交接 | **首选**：最安全，避免微信合规不确定性 |

3. **兼容性分析**：报告详细分析了每种可接受方案如何与现有架构对接——包括入站事件、出站请求、发送闸门、收件人映射、审批卡片和审计日志。

4. **明确拒绝路径**：报告明确拒绝了个人微信 SDK、扫码登录复活、实时个人账号自动化、桌面 UI 自动化、自动主动发送、隐藏记忆写入等路径。

5. **下一步建议**：
   - T231 应改写为一个选定官方平台的"合成入站合约刺探"——只定义数据合约，不接入真实 API
   - T232 应阻止真实出站发送，直到 T231 完成平台选择
   - T233 应改写为"提供者约束安全设计"，而非交付实现

### 对后续开发的意义

这个调研报告的核心结论是 `Gate M12 Conditional`——即 M12 不能作为"通用微信适配器"推进，但可以在极其严格的条件下探索单一官方平台。

这意味着：
- **个人微信自动化路线被正式永久封死**——不再尝试扫码、Hook 或任何非官方手段
- 如果要接微信，只能走企业微信客服或企业微信内部应用这种"企业级"官方路径
- 即使走官方路径，第一步也必须是纯合成的数据合约设计，而非真实 API 调用
- 在没有选定具体平台、没有企业账号、没有收件人映射模型之前，任何微信出站实现都被阻止

## 三、为什么给出 PASS 的评审结论

### 没有阻塞性问题

1. **任务目标完全达成**：任务包要求回答 6 个研究问题，报告逐一给出了明确答案。要求的 7 个输出章节全部存在且内容充实。

2. **没有违反禁止范围**：没有写代码、没有安装包、没有调用 API、没有使用真实凭据、没有读取私密聊天记录、没有修改任务板。三个产出文件全部在允许列表内。

3. **没有伪实现**：这是纯文档任务，不存在 mock/stub/hardcode 的可能性。

4. **没有破坏已有功能**：没有修改任何 `src/` 或 `tests/` 文件。

5. **文档没有把计划写成事实**：报告清楚地区分了"已确认的事实"和"需要未来验证的风险"。例如明确标注了"外部文档在 2026-05-28 查阅，未来实现任务前必须重新检查"。

### 非阻塞性观察

- 外部文档链接未由 Reviewer 独立重新获取验证（但 URL 格式正确、内容与公开认知一致）
- 选项矩阵每行是高维压缩，未来实现任务需要更深入的 API 合约分析
- 报告推荐了企业微信客服但没有做最终选择——这是合理的，因为最终选择需要用户/Captain 决策
- `channel_preference="wechat"` 的过度宽泛问题被正确识别但未提出具体子渠道方案

总的来说，这是一份严谨、保守、安全的研究报告，忠实地执行了"调研但不实现"的边界。
