# T152 Review Explained (通俗解释)

## 1. 这个 Task 在做什么？(通俗版)

想象你正在开发一个"智能回复助手"，它可以根据你和朋友的聊天历史，帮你起草回复草稿。在 M4 阶段（里程碑 4），我们已经让这个助手能够：

1. **记录你对草稿的反馈**：你觉得某个草稿好不好？要修改？还是完全不行？（T140）
2. **检查反馈记录是否合法**：比如你说"我要修改"但没有给出修改内容，这就是一个错误。（T141）
3. **汇总统计你的反馈**：比如你接受了 3 个草稿、拒绝了 2 个、修改了 1 个。（T142）

但问题是——这些功能虽然写好了，却**没有自动化的回归测试**。也就是说，如果以后有人改了代码，不小心把这些功能弄坏了，我们可能不会立刻发现。

T152 的任务就是：**给 M4 的反馈功能写一套完整的自动化测试**，确保未来任何改动都不会偷偷破坏这些已有的行为。

这就像给房子装上烟雾报警器——房子本身已经建好了，但我们需要一个可靠的机制来发现未来可能出现的问题。

## 2. 实现详细解释

### 2.1 任务目标

T152 的目标是：为 T140（反馈记录）、T141（反馈验证）、T142（反馈汇总）这三个已实现的功能，添加 60 个确定性回归测试，覆盖任务包中规定的全部 15 项测试要求。

### 2.2 任务流程

Worker 的工作流程是：

1. **阅读任务包**：理解需要测试哪些行为。
2. **构建合成测试夹具**：用 Python 代码直接构造测试数据，不读取任何真实聊天记录。每个测试数据都使用 `contact_test`、`replycand_test_001` 这样的安全合成 ID。
3. **编写测试类**：针对 15 项测试要求，逐个编写测试用例。
4. **运行全部测试**：确认 176 个测试（49 T150 + 67 T151 + 60 T152）全部通过。
5. **更新交接文档**：在 `docs/07_handoff.md` 中记录 T152 的实施记录，在 `docs/08_risks_and_open_questions.md` 中更新风险状态。

**测试文件结构**（`tests/test_feedback_cli.py`）：

- **辅助函数**：`_synthetic_reply_plan()` 创建合成的回复方案，`_write_plan()` / `_write_feedback_log()` 写入临时文件，`_make_record()` 构造反馈记录。所有临时文件使用 pytest 的 `tmp_path`，测试结束后自动清理。
- **TestFeedbackAppendAccept/Edit/Reject/Boundary**（10 个测试）：验证四种反馈类型都能正确追加到反馈日志。
- **TestFeedbackInvalidInputs**（4 个测试）：验证无效的候选项排名、缺失的方案文件、无效的 JSON 都会被拒绝。
- **TestValidationActionSpecific**（3 个测试）：验证校验器能发现"edit 但没有修改文本"和"boundary 但没有标签或备注"。
- **TestValidationPlanReference**（3 个测试）：验证校验器能发现缺失的方案引用、缺失的候选项、联系人 ID 不匹配。
- **TestSummaryAggregateCounts**（5 个测试）：验证汇总统计数字正确（总数、按类型计数、不同 ID 数量等）。
- **TestSummaryValidationMerge**（3 个测试）：验证校验报告的聚合数据能正确合并到汇总中，但不包含原始记录内容。
- **TestPrivacySafety**（7 个测试）：验证服务返回值、汇总输出、校验报告中都不包含私密文本（草稿原文、修改文本、用户备注、边界备注）。
- **TestNonMutation**（4 个测试）：验证反馈流程不会修改方案文件、验证和汇总是只读的、追加新记录不会影响已有记录。
- **TestPrivateOutputConfinement**（3 个测试）：验证非私有路径的隐私警告、非私有方案引用的警告、以及服务不强制输出路径限制（这是设计决策）。
- **TestCorruptedInput**（7 个测试）：验证损坏的 JSON、无效的 schema、缺失的文件在验证器和汇总器中都被显式上报。
- **TestCompactOutput**（4 个测试）：验证验证报告和汇总输出是紧凑的，不包含冗余的私密文本。
- **TestCLIAppendRegression / TestCLIValidateRegression / TestCLISummarizeRegression**（8 个测试）：端到端 CLI 回归，通过 Typer CLI Runner 直接调用命令行。

### 2.4 对后续开发的意义

1. **M4.5 回归硬化完成**：T150（ReplyPlanner 回归测试）、T151（策略夹具套件）、T152（反馈 CLI 回归测试）三个任务共同提供了 176 个已提交的确定性测试。这意味着从 git 仓库的内容就能证明系统行为是可复现的，不再依赖私有数据或手动验证。

2. **R046 可关闭**：干净环境可复现性风险（R046）是 M4 保持"有条件通过"的主要原因之一。现在这个风险可以关闭了。

3. **M5 可以被考虑授权**：任务看板明确规定"M4.5 完成后，船长可以重新考虑 M5 授权"。T152 是 M4.5 的最后一个任务，完成后项目可以推进到 M5（反馈到补丁建议）。

4. **为未来的重构提供安全网**：如果未来有人修改反馈服务、验证逻辑或汇总器，这 60 个测试会立即捕获回归问题。

### 2.5 风险更新

- **R046（干净环境可复现性）**：关闭。176 个测试覆盖了 ReplyPlanner、策略引擎和反馈 CLI 全部三个切片。
- **R042（损坏日志静默重置）**：已回归防护。损坏的 JSON、无效的 schema 和缺失的文件都会显式上报。
- **R043（路径处理）**：已回归防护。非私有路径的隐私警告已测试。
- **R044、R035、R037、R038**：保持活跃但不被 T152 范围覆盖。

## 3. 为什么给出 PASS_WITH_WARNINGS 的评审结果？

### PASS 的理由

1. **任务目标完全达成**：60 个测试覆盖了 T152 任务包中规定的全部 15 项测试要求。每一项都有对应的测试类和测试用例。

2. **没有伪实现**：测试直接调用真实的服务（`FeedbackService`、`FeedbackValidationService`、`FeedbackSummaryService`），没有使用 mock、stub 或硬编码的假成功路径。CLI 测试使用 Typer 的 `CliRunner` 直接调用命令行入口。

3. **隐私安全得到验证**：7 个隐私安全测试使用了独特的标记字符串（如 `unique_private_draft_marker_qwerty111`），通过 JSON 序列化后搜索这些标记来验证私密文本不会泄露到服务返回值、汇总输出或校验报告中。同时 `test_log_file_still_contains_private_text` 正确验证了私密数据仍然保存在私有日志文件中。

4. **非变异保证得到验证**：4 个测试验证了反馈流程不会修改方案文件、验证和汇总是只读的、追加新记录不会篡改已有记录。

5. **损坏输入显式上报**：7 个测试覆盖了损坏 JSON、无效 schema、缺失文件在验证器和汇总器中的显式错误上报。

6. **端到端 CLI 回归**：8 个测试通过 CLI Runner 直接调用命令行，覆盖了追加、验证、汇总三个命令的正常和异常路径。

7. **没有越界**：Worker 没有修改任何实现文件、没有读取 `private/chat_history/`、没有添加 mock、没有越界到 T160+ 的范围。

### WITH_WARNINGS 的理由

以下是 5 个非阻塞问题，它们不会阻止任务通过，但值得记录：

1. **N01 - `record_results` 列表仍无大小限制**：验证报告中的 `record_results` 列表包含每条记录的摘要（不含私密文本），但在大量反馈日志时仍可能变得冗长。测试验证了内容安全性（无私密文本泄露），但没有断言列表大小上限。这是 T141 遗留的 R045 风险。

2. **N02 - 输出路径限制仅在 CLI/警告层**：`FeedbackService` 允许写入任意路径，测试诚实地记录了这一设计决策。如果未来有多用户场景，需要在服务层增加路径限制。

3. **N03 - `--validation-report` CLI 标志缺少端到端测试**：这个标志只在服务层测试过，没有通过 CLI Runner 测试。服务层覆盖是充分的，但 CLI 接线未验证。

4. **N04 - 缺少跨服务流水线集成测试**：没有单个测试执行"追加反馈 -> 验证日志 -> 带校验报告汇总日志"的完整流水线。各环节独立覆盖是充分的，但组合正确性未被证明。

5. **N05 - `approach_labels` 断言较脆弱**：`test_approach_labels_loaded` 依赖特定的合成数据值，如果夹具结构变化会失败。这是有意为之的回归防护策略。

这些问题都不影响 T152 作为回归测试任务的完成性。它们要么是更早期任务的遗留问题（N01、N02），要么是边际价值较低的增量覆盖（N03、N04），要么是有意的测试设计（N05）。
